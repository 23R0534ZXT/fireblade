# Fireblade 0.2.0 — correctifs des huit constats d’audit

Les constats **FB020-01 à FB020-08 sont corrigés dans les sources** à partir de `a968e211ccef74cc44e99a8993762ae7201d0bf7`. Ce rapport du 4 novembre 2026 décrit les changements et les contrôles après correction. Les deux rapports précédents conservent leurs observations historiques : [première passe](20261103-v020-audit-complet.md), [seconde passe](20261104-v020-functional-audit.md).

**L’EXE 0.2.0 déjà publié reste inchangé.** Ces résultats concernent le code modifié dans ce checkout Linux ; ils ne constituent pas une nouvelle qualification du binaire Windows.

## Changements et régressions vérifiées

| Constat | Correction | Contrôle après correction |
|---|---|---|
| FB020-01 — parcours NTFS interrompu | Les chemins virtuels Dissect utilisent leur contrôle des liens/reparse points ; l’appel `is_junction()` reste réservé aux chemins natifs montés. | Une vraie image NTFS publique est parcourue sans erreur ; `$MFT` est extrait et l’image garde son SHA-256. |
| FB020-02 — journal SQLite omis | Copie groupée du fichier SQLite et des compagnons `-wal`, `-shm`, `-journal`, avec contrôle des empreintes et de la stabilité du groupe ; même contrôle groupé pour les LOG de ruches. Un groupe changeant est supprimé. | Une transaction validée seulement dans le WAL reste lisible dans la copie ; une modification injectée du WAL fait rejeter le groupe entier. |
| FB020-03 — SQL persistant lisant des fichiers externes | Nouvelle ouverture centralisée des analyses : accès externe DuckDB désactivé avant interrogation des objets, extensions automatiques désactivées, schéma et métadonnées vérifiés, macros persistantes refusées. Seul un import initial dans une base vide reçoit temporairement l’accès au CSV choisi. | Vues hostiles dans `events`/`metadata` refusées en ouverture directe et dans une archive à empreintes valides ; aucun case publié. Lecture externe également refusée après import, avec de fausses métadonnées de colonnes dérivées ou un lien dans le dossier temporaire. |
| FB020-04 — résultats d’une source modifiée publiés | La collecte classique retire ses nouveaux documents si le contrôle final de la source échoue, selon la politique déjà appliquée aux disques. | Après modification déterministe du CSV, statut du fichier `error`, zéro document sauvegardé et aucune session contenant l’analyse non vérifiée. Les fichiers de diagnostic peuvent rester dans le travail de collecte. |
| FB020-05 — dépendance IDNA vulnérable | `idna==3.15` épinglé dans les deux déclarations ; hôte brut limité à 253 caractères avant IDNA. L’outil local `pip` a aussi été mis à jour. | Tests de normalisation/IOC réussis ; une entrée Unicode trop longue n’appelle pas IDNA ; aucun avis connu dans le scan de l’environnement installé. |
| FB020-06 — export sur une preuve brute | La garde commune protège aussi les sources originales, archives et compagnons issus des inventaires de collecte actifs ou sauvegardés, ainsi que les alias par identité de fichier. | ZIP brut et lien physique refusés pour une collecte active puis inactive ; les octets restent identiques. |
| FB020-07 — export Hayabusa non protégé | Cet export appelle la garde commune et publie par remplacement atomique après copie vers un temporaire. | Source CSV conservée si choisie comme destination ; panne de copie simulée : ancienne destination intacte et temporaire supprimé. |
| FB020-08 — écrasement des fichiers internes | Sessions Fireblade/TLE et règles globales passent par la même garde que CSV et les autres exports ; protection du manifeste, états, règles, verrous, sessions internes et historique. | Les seize combinaisons écrivain/destination sont refusées ; les quatre écrivains réussissent toujours vers de nouveaux fichiers externes. Alias physique de `case.json` également protégé. |

La garde est aussi appliquée à l’export portable dans le moteur. Elle refuse une destination dans un répertoire source de collecte et vérifie les inventaires sauvegardés ; un inventaire malformé empêche l’export au lieu de désactiver sa protection. Un inventaire absent reste un diagnostic de couverture et permet de récupérer les autres analyses du case.

La désactivation de l’accès externe a nécessité d’adapter deux transferts légitimes : les instantanés portables et le pont CSV de construction de chronologie passent désormais par l’espace temporaire propre à l’analyse. Leurs fichiers sont nettoyés après utilisation. Les colonnes calculées, fonctions .NET approuvées, bases simultanément ouvertes, annulations et transports entre cases sont inclus dans les tests.

Deux modules ajoutent **38 cas de régression** : [moteur](../../../tests/core/test_audit_regressions.py) et [interface](../../../tests/ui/test_audit_export_protection.py). Le volume NTFS public est conservé compressé avec [provenance, empreinte et licence](../../../tests/fixtures/disks/SOURCES.json), afin que son test ne dépende pas du réseau.

## Reproduction

Depuis la racine du dépôt, avec les dépendances de développement installées :

```bash
.venv/bin/python -m pytest -q tests/core/test_audit_regressions.py tests/ui/test_audit_export_protection.py
.venv/bin/python -m pytest -q --durations=20 -ra
.venv/bin/ruff check src scripts tests
.venv/bin/python -m pip check

PYTHONPATH=src .venv/bin/python -m scripts.benchmarks.audit_v020 \
  --directory /tmp/fireblade-fixed-independent \
  --large-directory /chemin/benchmark-3gib --disk-fixtures /chemin/disques-publics

PYTHONPATH=src .venv/bin/python -m scripts.benchmarks.audit_functional \
  --directory /tmp/fireblade-fixed-workflows \
  --hayabusa-source /chemin/pack-verifie/Hayabusa-source.zip

PYTHONPATH=src .venv/bin/python -m scripts.benchmarks.benchmark_timeline \
  --directory /tmp/fireblade-fixed-timeline --rows 500000
```

Les tests .NET nécessitent `DOTNET_ROOT`, `FIREBLADE_DOTNET`, `FIREBLADE_PLUGIN_HOST`, `FIREBLADE_PLUGIN_FIXTURE` et `FIREBLADE_SHELLBAGS_HOST`, pointant vers un SDK et les hôtes construits. Le gros CSV est celui du benchmark `--gib 3.05`, vérifié lors du premier audit ; la matrice de disques utilise les fixtures publiques documentées dans ses preuves. Les deux scripts d’audit renvoient désormais zéro lorsque toutes leurs reproductions sont corrigées.

## Limites avant publication

Quatre contrôles pytest restent propres à Windows (chemins longs, UNC/SMB, LocalAppData natif et verrouillage de fichier). Le test paramétré d’encodage GIF reste ignoré, l’encodeur Qt étant absent ici ; le décodage GIF a été exercé séparément lors de la passe précédente. Les limites natives de SQLECmd, WxTCmd et SrumECmd décrites dans le second audit subsistent dans cet environnement Linux.

La construction Python vérifie le module ajouté et la dépendance corrigée. Avant de diffuser un exécutable corrigé, il reste à reconstruire et qualifier la distribution sous Windows avec les scripts du dépôt, puis à refaire les contrôles natifs et de publication. Aucun nouvel EXE, tag ou actif de release n’a été publié par ces travaux.
